# 설계 결정 기록 (Architecture Decision Records)

> 어떤 결정을 했고, 왜 했는지, 언제까지 유효한지를 기록합니다. 번복을
> 원한다면 여기서 근거를 먼저 반박하세요.

## D1 — 타겟은 공무원/문서 중심 지식노동자

**결정:** 1순위 페르소나는 한국 공무원 및 문서 중심 업무를 보는 지식노동자.
HWP·HWPX·PDF·DOC는 출시일부터 필수 지원.

**근거:**
- 기존 솔루션이 전부 API 기반 → 공무원은 보안 규정상 사용 불가 → 수요가
  실존하나 대안이 없음.
- HWP 생태계를 안 다루는 도구는 업무 흐름 진입 자체가 불가능.
- "과거 문서 재활용"의 가치가 이 집단에서 가장 큼 (연간 인수인계 수요).

**번복 조건:** 국내 HWP 점유율이 급락하거나, 해외 시장 진출이 우선순위가
될 때.

## D2 — 한컴 COM 자동화 사용 금지

**결정:** HWP 파싱에 `pywin32 + Hancom Office COM` 경로를 사용하지 않음.
모든 파서는 순수 Python.

**근거:**
- Windows 전용이어서 크로스플랫폼 원칙(D7)을 깸.
- 한컴 오피스 라이선스를 전제 → OSS 배포 원칙(D8) 훼손.
- 서비스 로그인 세션이 없으면 동작하지 않음 → 서비스 실행 시 불안정.
- 모달 대화상자 등 UI가 나타나면 headless 환경에서 무한 대기.

**트레이드오프:** 복잡한 레이아웃(수식, 도형, 플로트)이 일부 손실됨.
`warnings`에 명시해서 사용자가 인지 가능.

**대체 전략:** HWPX는 XML이라 완전 파싱, HWP 5.x는 `pyhwp`로 텍스트+단순표,
HWP 3.x 이전은 파일명 스텁.

## D3 — 원본 파일을 서버에 복제하지 않음

**결정:** 인덱스는 경로·해시·추출 텍스트만 저장. 바이너리 원본은 제자리.

**근거:**
- 프라이버시: 서버(디스크) 탈취 시 노출 범위를 문서 내용 요약 정도로 한정.
- 디스크 용량: 10만 문서라도 인덱스는 ~15GB 내외.
- 신뢰: "이 앱이 내 파일을 어디로 옮겼는가?"에 대한 답이 항상 "안 옮김".

**번복 조건:** 다기기 동기화를 지원할 때. 그때도 opt-in이어야.

## D4 — 네트워크 접근 없음 (localhost 전용)

**결정:** 모든 IPC는 127.0.0.1. LAN 공유, 원격 접속 기능 없음. 모델 다운로드는
`scripts/download-models.py` 실행 시에만 egress.

**근거:**
- 공격면 최소화. 방화벽 예외 불필요.
- 공무원 업무망에서 네트워크 바인딩 자체가 조사 대상 될 수 있음.
- "왜 이 앱이 포트를 열고 있는가?"에 대한 해명 불필요.

**번복 조건:** 팀 공유 기능을 넣을 때(현재 계획 없음). 그때도 별도 모드.

## D5 — 범위는 L1 (문서 전용)

**결정:** 화면 캡처, 클립보드 기록, 브라우저 히스토리 포함하지 않음.

**근거:**
- MS Recall이 유발한 신뢰 이슈를 반면교사로 삼음.
- 공무원은 "문서를 찾고 싶다"는 명시적 수요, 포괄적 감시에 대한 수요 아님.
- 범위가 좁을수록 도입 저항이 작음.

**번복 조건:** 없음. 확장이 필요하면 별개 제품으로.

## D6 — 1인 1머신

**결정:** 멀티 사용자, ACL, 권한 구분 없음.

**근거:**
- 초기 복잡도 3배 감소.
- 공무원 실제 워크플로는 개인 PC 중심.
- 팀 공유는 미래 기능으로 언제든 별도 에디션으로 분리 가능.

## D7 — 데스크톱 앱, 단일 설치파일

**결정:** Tauri 기반 데스크톱 앱. Windows MSI / Linux AppImage. 웹 전용
배포 없음.

**근거:**
- 글로벌 단축키, 파일 열기, 트레이 아이콘 같은 OS 통합이 UX 핵심.
- AppImage는 패키지 매니저 없는 공무원 PC에서도 더블클릭 실행 가능.
- Tauri는 Electron 대비 설치 용량 ~1/5, 메모리 사용 ~1/3.

## D8 — AGPL-3.0 코어

**결정:** 라이선스는 AGPL-3.0-or-later (코어), MIT (파서 플러그인).

**근거:**
- 공무원 도입 시 "오픈소스이며 감사 가능"이라는 신뢰 이점.
- AGPL은 SaaS 무단 포크를 억제하면서 내부 사용과 수정은 완전 허용.
- 파서는 커뮤니티 확장이 기대되는 부분이라 MIT로 장벽을 낮춤.

## D9 — 엄격 근거 (Strict Provenance)

**결정:** RAG 답변은 반드시 근거 문서 각주를 포함. 근거가 없으면 정확한
sentinel 문장으로 "답변 불가"를 선언.

**근거:**
- 법무·공무원 도메인에서 환각 한 번이 신뢰를 영구 회복 불능으로 만듦.
- 사용자가 "이 정보 어디서 왔어?" 를 언제나 검증 가능해야 함.
- LLM 오류가 업무 결재·감사 서류에 흘러가면 개인 책임이 됨.

**구현:** `core/eoditdeora/runtime/prompts.py`의 `RAG_STRICT_SYSTEM` 프롬프트와
`core/eoditdeora/retriever/rag.py`의 sentinel 탐지.

## 기술 스택 (비결정적이지만 초기값 고정)

| 영역 | 선택 | 대안 검토 필요 시점 |
|---|---|---|
| UI 셸 | Tauri 2.x | Electron 비교가 필요하면 재논의 |
| UI 프레임워크 | Svelte 5 | React로 갈아타는 비용 낮음 |
| Core 언어 | Python 3.11+ | Rust 포팅은 파서 생태계 손실 큼 |
| LLM 런타임 | llama.cpp + Vulkan | ROCm는 Linux 전용, vLLM은 Windows 지원 약함 |
| 벡터 DB | LanceDB | Qdrant 임베디드 성숙 시 비교 |
| FTS | Tantivy | Meilisearch는 별도 프로세스라 제외 |
| 토크나이저 | Kiwi (kiwipiepy) | mecab-ko는 설치 까다로움 |
| 해시 | xxhash 64 + sha256 | — |
